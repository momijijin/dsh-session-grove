# dsh-session-grove 0.4.0-beta.65

A dialog keyboard-timing fix, a row-menu scroll-stability fix and an
architecture-debt cleanup batch. The latest published release is
`0.4.0-beta.64` (2026-11-12); `0.4.0-beta.65` is a `dev` batch that is **not
tagged or published** (local batch date 2026-11-13).

No public API, control-protocol, storage-format, locale resource, test id, CSS
or ARIA contract changed; the only behavior change is the S7 menu scroll-close
bug fix. `DOC_VERSION` stays 1, the 21-key host integration surface is
unchanged, and the 397 keys in 19 dictionaries are untouched. `lib/client.js`
is rebuilt from source by `npm run build` and carries the `.65` version stamp.

## Dialog keyboard timing

- Failure symptom: the isolated suite could fail at
  `keyboard dialog move did not move right` right after the dialog opened. The
  arrow key was consumed but the dialog did not move, or focus had already left
  the titlebar/resizer, so the key handler never ran.
- Two candidates were identified and both are addressed:
  1. **Focus loss before the arrow key.** The dialog seeded focus through two
     paths — the `[dialog]` effect and a duplicate 10ms input-focus timer in the
     seed effect — so a late timer could steal focus from the titlebar/resizer
     the test had just focused.
  2. **Rect timing before the geometry lands.** `dialogRectRef.current` is empty
     only when no rect has been saved yet (the first open of a dialog without
     persisted geometry); a persisted geometry fills it at open. A keyboard
     gesture arriving before the first measurement therefore read `null` and
     did nothing even though the dialog was visible and marked positioned.
- e2e (`e2e/isolated.spec.mjs`): the dialog now waits for
  `data-positioned="true"` before the keyboard section, and the new local
  `focusAndSettle` helper focuses the titlebar/resizer, settles 150ms, retries
  once, and asserts `document.activeElement`. A failure reports the
  `activeElement` test id instead of a bare "did not move" line.
- Plugin focus guard (`src/client/dialog-host.js`): the duplicate 10ms seed
  timer is gone; the single deferred focus runs through
  `shouldFocusDialogTarget(activeElement, dialogElement)`, which skips the focus
  write when focus is already on a dialog descendant (and still focuses when
  focus is `null`, `body`, an outside element or the dialog itself). Inline
  error re-dispatches therefore no longer pull focus out of an input.
- Rect fallback (`src/client/dialog-geometry.js` + `dialog-host.js`):
  `dialogRectFromElement` adapts a measured rect but rejects non-finite or
  non-positive sizes; `resolveDialogRect` prefers the persisted/ref rect and
  otherwise clamps the measured one. `currentDialogRect()` feeds the gesture and
  the keyboard move/resize paths, so the first arrow key works before the
  geometry effect has stored a rect. The fallback is not persisted: once a rect
  exists, the existing keyup `persistDialogRect()` saves it as before.

  shell only — slot lifecycle, width/layout, workspace chrome, settings/styles

  geometry, focus guard, Tab/Escape, gestures, keyboard handling, body

  drives the registry diagnostics and `src/host/storage-health.js`, so the
  doctor report cannot drift from the registry's own verdict.

  constant directly; the `DEFAULT_PROFILE_LIMIT` alias (and its dead export) is
  removed.

## Menu scroll stability (S7)

- Symptom: with a group/session row menu open, scrolling the conversation pane
  on the right dismissed the menu immediately. During streaming that pane
  auto-scrolls to follow the output, so the menu kept closing right after it
  opened and only became stable once the stream ended; scrolling the left tree
  was unrelated to the report.
- Root cause: `src/client/plugin-host.js` listened for `scroll` on `document`
  in the capture phase and dispatched `menu: null` for any scroll unless the
  target was inside `.dsg-menu` / `.dsg-dialog`. The conversation pane is not an
  ancestor of the menu's source row, but its scroll event still reached the
  document capture listener, so the anchor was treated as stale. The menu state
  itself was never cleared by streaming: the `doc` and `load-success` branches
  of `state.js` spread `...snapshot` and keep `menu`; only a profile switch sets
  `menu: null` explicitly.
- Fix: the scroll-to-close owner is now `MenuPopover` in
  `src/client/session-menu.js`. While a menu is open it caches
  `menuSourceRow(menu)` once and decides with the pure
  `scrollAffectsMenu(target, row)` helper (moved with `menuSourceRow` into
  `src/client/groups-view-menu-handlers.js`): a missing/detached row, a missing
  target, `document`/`window` and targets without `contains` close; otherwise
  only `target.contains(row)` — a scroll of the row's own ancestor containers —
  closes. A missing or detached row gets exactly one re-query before that
  decision.
- Performance: for an unrelated scroll the path reads no layout
  (`getBoundingClientRect` / `getComputedStyle` / `offset*` / `scrollTop`),
  performs no `querySelectorAll` and dispatches nothing. Each scroll costs at
  most one `target.closest('.dsg-menu, .dsg-dialog')` ancestor check, plus one
  `menuSourceRow` re-query when the cached row is missing or detached (see
  above). The streaming auto-scroll therefore cannot re-render the groups view;
  the decision is O(1).
  The listener exists only while the menu is open
  (`{ capture: true, passive: true }`, removed on close), and `plugin-host.js`
  keeps only resize closing (`closeMenuOnResize`) — the document scroll
  listener is gone, so there is no double listener.
- Tests: unit/contract **1031/1031 PASS** (+4 from the 1027 of the sections
  above; the new `tests/client/menu-scroll.test.js` pins every
  `scrollAffectsMenu` branch with a throw-on-read layout trap plus
  `menuSourceRow` hit/miss); UI runtime **45/45 PASS**; `check:style` **PASS**
  (228 files); the source assertions in `tests/client/ui-layout.test.js` move
  the scroll listener to `session-menu.js`, require resize-only in
